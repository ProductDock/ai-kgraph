- **Stage:** 3 — plan & design review

## Context

`ai-kgraph` is today a documentation-and-automation repo for the AI-Native SDLC: `docs/`,
`intent/`, `.claude/skills/` and two GitHub workflows. The intent's problem is that every
new Next.js project re-derives the same structural decisions from memory, so each result
comes out subtly different and an evening is spent before any product work happens.

This change turns the repo into a running Next.js App Router application **added around**
the existing tree — nothing existing moves, because five documented couplings (workflow
path filters, skill relative links, hard-coded `intent/<slug>/…` paths, the `**Status:**`
`grep`/`sed`) break if `intent/`, `docs/` or `.claude/` move (spec §3.1). The SDLC trees
become app *content* by being **read in place, read-only, at build time**, not by being
migrated.

The deliverable is a foundation, not a feature: no product screens, no data layer, no
auth, no content rendering. What ships is the seam those attach to, plus every structural
decision written down on disk and in `CLAUDE.md` so it is never re-decided.

### §13 handoff items resolved

1. **Tailwind major: v4.** `tailwindcss@4.3.3`, CSS-first configuration — no
   `tailwind.config.ts`; `@import "tailwindcss"` plus `@theme inline` in `globals.css`,
   and `@tailwindcss/postcss` in `postcss.config.mjs`. `shadcn@4.21.0` emits v4 output.
   `tailwind-merge@3.x` is the v4-matching major. This answers R-2 before any CSS exists.
2. **TypeScript pins to `6.0.3`, not the `latest` `7.0.2`.** `eslint-config-next@16.3.4`
   depends on `typescript-eslint@^8.46.0`, whose peer range is `>=4.8.4 <6.1.0`. TS 7
   would break `npm ci` peer resolution and typed linting. `6.0.3` is the newest stable
   release inside that range. Re-check when `typescript-eslint@9` ships.
3. **Node pins to 24 LTS.** `vitest@5` engines are `^22.12.0 || ^24.0.0 || >=26.0.0`, so
   the machine's active `v25.8.0` is out of range regardless. `.nvmrc` = `24`, `engines.node`
   = `>=24.0.0 <25.0.0`. One-time `nvm install 24` on this machine; `nvm use` then reads
   `.nvmrc`. CI uses `node-version-file: .nvmrc`.

## Sequence of work

Each step is independently verifiable. This follows spec §13's suggested sequence with
**one deliberate deviation, in step 3** — see below.

1. **Toolchain + scaffold.** `nvm install 24 && nvm use 24`. Run
   `npx create-next-app@16.3.4 <scratch> --ts --tailwind --eslint --app --src-dir --import-alias "@/*" --use-npm --yes`
   in the scratchpad, **not in the repo** — `create-next-app` refuses a directory holding
   `docs/`, `intent/`, `.claude/`, `.github/`. Copy the generated config and `src/app`
   skeleton in, drop `AGENTS.md`, rewrite `package.json` to the exact pinned set, `.nvmrc`,
   `engines`. Harden `tsconfig.json`. → **V-1, V-2, V-3**
2. **`cn()` + the Tailwind v4 confirmation.** Write `src/lib/utils.ts` verbatim; assert
   `tailwindcss@4` and `tailwind-merge@3` resolved as planned before any CSS is authored.
   → **V-9**
3. **shadcn init, *then* author the tokens.** ⚠ *Deviation from §13's ordering, which puts
   tokens before the shadcn seed.* `npx shadcn@4.21.0 init` **rewrites `globals.css`** with
   its own semantic variables and `@theme inline` block. Authoring §7.3's role-named tokens
   first means writing them twice. So: `init`, add `button card skeleton`, and only then
   author the role-named light/dark tokens and map shadcn's semantic names onto them inside
   `@theme inline`. Add the pre-paint theme script, `:focus-visible` ring and the global
   `prefers-reduced-motion` rule. → **V-12**
4. **Route shell.** `layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx`,
   `global-error.tsx`, `not-found.tsx`, each with real content, plus the skip link and the
   single `<h1>`. → **V-6, V-16**
5. **Env module.** `src/lib/env.ts` with both zod schemas and the browser-read Proxy guard;
   `.env.example`; `src/types/env.d.ts`. → **V-7, V-10**
6. **Providers + the state boundary.** `providers.tsx` as the only client boundary,
   `lib/query/client.ts` + `keys.ts`, `stores/ui-store.ts`, `components/common/theme-toggle.tsx`,
   `hooks/use-mounted.ts`. → **V-11**
7. **`lib/api/` + `types/`.** Typed fetch wrapper, `ApiError`, shared types.
8. **Lint, format, test.** `eslint.config.mjs`, Prettier config, `vitest.config.ts` +
   setup, the three tests. → **V-4, V-5, V-13**
9. **`CLAUDE.md`.** Written from what now exists on disk, not from intent — it must describe
   the built thing. → gate for "done" per §10
10. **Headers + CSP Report-Only.** `next.config.ts` `headers()`. HSTS is written but left
    **commented with a reason**, since no TLS host exists (C-6). Nonce middleware is *not*
    added — it would force dynamic rendering on every route with no report collector to
    justify it. → **V-8**
11. **Content seam.** `src/lib/content/types.ts` + `read.ts` with allow-listed slug
    resolution, and its traversal test. No route consumes it.
12. **`verify.yml`, `.gitignore`, `README.md`.** Then the full fresh-clone proof run. →
    **V-14, V-15**

Then: commit `intent/nextjs-project-baseline/plan.md` on `plan/nextjs-project-baseline`
referencing #6 — **before** any of the above is written.

## Risks

| ID | Risk | Mitigation in this plan |
|---|---|---|
| **R-A** | **shadcn `init` overwrites hand-authored `globals.css`.** Riskiest step (3). If done in §13's order, the tokens are silently replaced and the failure looks like "dark mode stopped working". | Ordering inverted deliberately: generate first, author tokens second, bridge via `@theme inline`. If `init` output still surprises, `globals.css` is one file — re-author it; nothing else depends on its internals. |
| **R-B** | **TypeScript 7 exists and looks like the right pin.** Taking `latest` breaks `npm ci` peer resolution and typed lint. | Pinned `6.0.3` with the reason recorded above, so the next person doesn't "helpfully" bump it. |
| **R-C** | Client boundary drawn wrong → whole app becomes a client bundle, silently, with no error (spec R-3). | `providers.tsx` is the only `'use client'` file in the root tree; `children` passed as a prop, never imported. In `CLAUDE.md` pitfalls. |
| **R-D** | Module-scope `QueryClient` on the server leaks one request's cache into another — a data-isolation bug, not a performance one (spec R-4). | `makeQueryClient()` in `lib/query/client.ts` is the only construction site; `useState(makeQueryClient)` in the provider. In `CLAUDE.md`. |
| **R-E** | **`.gitignore` anchoring is the only non-additive edit.** | The two workflows write those scratch files to the runner **workspace root**, which the anchored patterns still match — no SDLC behaviour changes. V-15 confirms no workflow file changed. |
| **R-F** | `verify.yml` now also runs on the spec-bot's own commits and on every PR. | Correct and harmless: the job is pure, `contents: read`, and `cancel-in-progress: true`. It does not alter when the two existing workflows fire. |
| **R-G** | **Spec §8 is not organisational policy** (C-1) — no security policy skill exists in this repo and §8 has had no policy-owner review. | Stated here, and in the PR. Follow-up intent for the policy skills. Nobody should read V-8 as proof of a hardened app; the baseline is *prepared to be secured*, not secured (C-6). |
| **R-H** | The `dataviz` placeholder palette and system font stack harden into the de facto brand (C-2, spec R-6). | Role-named tokens only, so a brand swap is a values-only edit. Follow-up intent filed. A substituted palette must be re-validated with `dataviz`'s `validate_palette.js` against `ai-kgraph`'s own surfaces. |
| **R-I** | Scope creeps into the product surface (D-3 / C-4, spec R-5). | §2.2 is explicit; the content seam ships with **zero consumers**. Anything beyond it is a new intent. |
| **R-J** | Vendored `components/ui/**` is invisible to dependency automation, so it only updates deliberately (C-7). Bus factor is one. | Recorded in `CLAUDE.md` as an explicit rule. Dependency automation (D-7) is *not* configured in this change — it needs its own decision. |

### What existing behaviour this breaks

Nothing that runs today. The two workflows install `@anthropic-ai/claude-code` globally and
never run `npm ci` in the repo, so a root `package.json` cannot interact with them (spec
R-1, confirmed by V-15). The skills' relative links (`../../../docs/…`) still resolve
because nothing moves. The single behavioural change outside the app is the `.gitignore`
anchoring (R-E), which narrows ignore scope rather than widening it.

### Rollback

Every change is additive except that one `.gitignore` edit. Reverting the merge commit
restores the repository exactly: no data migration, no deployed surface to drain, and the
SDLC machinery is untouched throughout, so there is nothing of it to roll back.

### Open questions this plan does *not* close

- **D-3 / C-4 — what the knowledge app actually does** with the SDLC docs. Deliberately
  unanswered; it is a product question and gets its own intent. The baseline is therefore
  built without knowing what it must eventually carry — search implies an index, graph
  visualisation implies a parse-and-relate step, and either may imply the persistence D-5
  put out of scope. `src/lib/content/` is a seam, not insurance.
- **C-10 — personal data in `intent/**`.** `intent.md:3` carries a name and a live work
  email. Not a blocker here (nothing renders), a blocker for the first content route.
  Follow-up intent.
- **C-6 — CSP enforcement and HSTS** cannot be completed without a deployment target.
  Report-Only ships; enforcement is a later decision.

## Proof

Run in order on a **fresh `git clone`**, no manual intervention beyond `nvm use`. This is
the Stage 4 feedback loop.

```bash
git clone <repo> /tmp/verify-baseline && cd /tmp/verify-baseline
nvm use                                          # V-1  reads .nvmrc → v24.x
node -v                                          # V-1  matches .nvmrc major
npm ci && git diff --exit-code package-lock.json # V-2  exit 0, lockfile unchanged
npm run typecheck                                # V-3  exit 0   ← intent requirement
npm run lint                                     # V-4  exit 0
npm test                                         # V-5  exit 0 (includes V-9, V-13)
cp .env.example .env.local
npm run dev & sleep 5
curl -sf -o /dev/null -w '%{http_code}\n' localhost:3000   # V-6  200 ← intent requirement
curl -sI localhost:3000 | grep -iE 'x-content-type-options|referrer-policy|x-frame-options|permissions-policy|content-security-policy-report-only'  # V-8  all present
kill %1
rg -n 'process\.env\.' src --glob '!src/lib/env.ts'        # V-7  no matches
grep -v NEXT_PUBLIC_APP_URL .env.example > /dev/null; env -u NEXT_PUBLIC_APP_URL npm run build   # V-10 non-zero, names the var
npm run build                                    # V-14 exit 0
rg -n 'NODE_ENV.*server-only|serverEnv' .next/static  # V-11 no matches
git diff --stat main -- .github/workflows/spec-from-intent.yml .github/workflows/plan-ready.yml .claude/skills/   # V-15 empty ← constraint check
```

Two checks are observational and recorded in the PR:

- **V-12** — with the OS in dark mode, load `/` and record first paint: no light frame.
- **V-16** — tab through `/`: the skip link is the first stop, focus is visible on every
  interactive element, and the theme toggle is operable and announced.

**V-3, V-6 and V-15** are the three that map directly to the intent's own stated
requirements. If V-15 is non-empty, the change has violated the intent and must be reverted,
not patched.

### Could another engineer implement this without asking a question?

Yes, with one caveat worth stating rather than hiding: the exact `globals.css` produced by
`shadcn init` under Tailwind v4 is not knowable until it is run (R-A), so step 3 is
"generate, read the output, then bridge" rather than a file that can be written blind.
Everything else — versions, paths, file responsibilities, ordering, proof — is fixed above.
